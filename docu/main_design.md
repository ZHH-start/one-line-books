# 设计理念

本章描述产品的设计目标与导向，是后续一切章节的上游。任何功能、字段、分类的存废争议，回到本章裁决。
### 用户画像

**不为"管钱"，只为"知道钱花哪了"的人。愿意花 5 秒说一句话，不愿意花 30 秒点表单。**

主要用户是开发者本人，次要用户是非技术用户。
### 核心设计：简约，只有记账

只做"记账"工具，不当"理财"工具。理财管的是资产（多账户、对账、预算、还款）；记账只回答两个问题：**"这个月花了多少"、"都花在哪了"**。凡属于理财的功能，一律不做。

**语义唯一，语法宽容**：分类、数据格式固化，用户感知不到；输入格式给建议不给强制，解析不了就提示让用户修正。

**核心数据本地化**：全部数据纯本地存放。服务器不存取数据，只负责更新软件版本。

**数据管理简单化**：就是一份 Markdown 文档，可导出可导入，可直接阅读手改。

**纯前端**：一组无构建的静态文件（`index.html` + 若干 JS/CSS 模块文件 + `icon.png` 等图标资源），扔到任何静态服务器都能跑。文件按模块拆分，更新问题由版本检查机制兜底，可维护性优先。

# 核心交互流程

## 记一笔（主流程）

```text
用户输入自然语言 → 调用 LLM 解析 → 写入数据 → 回显确认
```

AI 记完必须立即回显结构化结果，例如：

> 已记 2 笔：餐饮 35.00（午饭）｜ 餐饮 18.00（咖啡）

回显即纠错入口：用户扫一眼就知道对不对。
## 调整录入内容

允许用户对话式纠错。为了降低解析出错的风险，用户在**记账时允许自由表达，而调整时必须以"更正""删除"开头**。没有指定记录则默认上一条，否则按指定日期或内容定位。

举例：

- 用户："更正：是 260" → 修改上一条记录金额。
- 用户："删除：10月1日午饭" → 删除指定记录。
- AI 回显："更正：已记 2 笔：餐饮 45.00（午饭）｜ 餐饮 18.00（咖啡）"

兜底：**手动编辑**——明细页与记账页的条目可编辑（金额、分类、日期、备注等）、可删除。
## 模糊处理

AI 拿不准、缺失必要信息时拒绝记录，**必须附带而且只附带拒绝原因**，让用户能立即纠正。例如："未记录金额：无法记入，请补充说明"。
## 对话记录

用户输入与 AI 回显构成对话流（微信式）。**对话记录按账本隔离**：每个账本一份md文档。

对话记录缓存**不参与导出导入，不属于账本 md**，清除缓存、更换手机即丢失。
## 容错

AI 请求一律使用**流式响应**（`stream: true`），容错按以下故障形态处理：

- **发送/停止一体按钮**：发送后发送按钮变为停止按钮，点击即中断请求（AbortController）。用户随时可手动掐断。
- **状态气泡**：AI 侧气泡实时显示所处阶段——"思考中"（已连接，等待首个内容 chunk）→"回复中"→ 弹出记账信息，完成。用户一眼能区分"模型在干活"与"模型没动静"。
- **首 token 超时**：进入"思考中"后 30 秒内未收到任何内容 chunk（连接正常、有心跳但无产出，即"模型无响应"故障）→ 气泡转为"AI 无响应"，判定发送失败。首 token 一旦到达则不再设总时长限制——模型慢但在持续输出时不干预（兼容响应慢的模型服务）。
- **失败可编辑重发**：凡未正常完成（断网、HTTP 错误、AI 无响应、手动停止），最后一条用户消息可就地编辑并重新发送；每次重新打开询问是否处理。
- **API 未配置**：用户尝试对话时引导用户去设置页，否则对话不可用。但不阻塞浏览已有数据。
# 后台数据模型

## 存储

账本数据是一份份 **Markdown 文档文本**：**一个账本 = 一份 md**。全部账本存放于浏览器 localStorage（每个账本一个键，另存"当前账本"指针）。App 内所有展示、统计均只针对当前加载的账本，账本之间完全独立文件。

## 账本头

md 文档开头是账本配置（自描述，文件搬到哪配置跟到哪），空行之后才是记录。配置文件结构举例如下：

```text
-----------------
账本：生活账本
模板：生活
支出分类：餐饮、交通、购物、居家、娱乐、医疗、教育、通讯、人情、其他
收入分类：工资、理财、其他收入
储蓄目标：3500/月
默认分类规则：
- 吃进肚子的（含买菜、食材、外卖、奶茶） - 餐饮
用户分类规则：
- 买螺丝刀 - 交通
-----------------

2026-10-01 | 支出 | 餐饮 | 35.00 | 午饭
2026-10-15 | 收入 | 工资 | 9200| 
2026-10-17 | 支出 | 购物 | -200| 衣服购买退款
```

解析规则：第一条符合日期格式的记录行之前的全部内容视为账本头。账本头分"默认分类规则"与"用户分类规则"两个区，各区之下每行一条规则，格式为 `- 规则 - 分类`。导入时，读文件建立账本配置，作为新账本加入。

## 记录格式

字段：日期 | 类型 | 分类 | 金额 | 备注

- 日期：YYYY-MM-DD
- 类型：`支出` / `收入`
- 金额：两位小数；退款为负值，其余非负
- 备注：任意文本，不含竖线；渠道、目的、商户、资产移动性质等信息均在此承载

设计参考：一行一条，竖线分隔，追加式，行首无修饰符：

```text
2026-10-01 | 支出 | 餐饮 | 35.00 | 午饭
2026-10-01 | 收入 | 工资 | 8500.00 | 十月工资
```

## 退款

退款**不记收入**，记为对应支出分类的**负金额支出**：

```text
2026-10-01 | 支出 | 购物 | -59.00 | 衣服退款
```

使分类统计反映净花销。这是数据格式的硬约定。
## 资产移动

转账、垫付、借贷按『资产移动的处理』规则记为普通收支，备注写明性质（"垫付""收回""借给某人""某人还钱"），不引入新类型。
## 导出与拆分

导出分为部分导出和完整导出两个方式。部分导出要求选中时间跨度，而完整导出相对简单，直接导出整个文档即可。

完整导出时，把当前账本（或其时间范围子集）下载为 md 文件，原件不动。

部分导出时，可按时间范围选择（如只导出几个月）。选中的时间范围从原账本**移出**，生成带新账本头的独立 md 文档。并要求输入导出账本的名字。默认名字就是导出时间范围。用户也可以手动修改。
# 分类体系

**分类配置属于账本，不属于 App。** 每个账本的 md 文档头部声明自己的分类表（见『账本头』），AI 只能从当前账本的分类表中选择，禁止自创。分类按对象不按目的，参考『分类原则：按对象，不按目的』。

用户可直接编辑当前账本的分类表（设置内编辑，或直接手改 md 头部）

**预设模板**（新建账本时选择，模板只是初始分类表，之后可自由修改）：

- **生活**：餐饮、交通、购物、居家、娱乐、医疗、教育、通讯、人情、其他（收入：工资、理财、其他收入）
- **项目/研发**：物料、生产、研发、外包、差旅、其他（收入：项目款、报销、其他收入）

也允许用户自定义

每个分类表的最后一项固定为"其他"，作为兜底。
## 分类判定规则（写在账本头，跟着账本走）

每个账本有自己的分类规则，存放在账本头的"分类规则"区，分两层：

- **第一层（默认规则）**：新建账本时由模板写入。默认内容为消歧优先级"无法确认时，用途大于功能"，典型裁决：吃进肚子的（含买菜、食材、外卖、奶茶）→ 餐饮不算购物；购买实物商品（非食物）→ 购物；居住相关（房租、水电、物业）→ 居家。
- **第二层（用户强制指令）**：开放。用户发现 AI 反复分错时，在设置页的文本框里直接写强制指令，一行一条，自然语言即可（如"打气筒划分到购物"），ai按照约定的字段结构追加到账本头分类规则区。**用户指令优先于默认规则，AI 必须服从。**

**禁止猜测**：按规则仍无法确定分类时，AI 不得自行选择，必须按『模糊处理』规则回复用户，要求用户指定分类。

注：不做跨记录的"分类记忆"——一次性物品居多，永久记忆的 token 成本不合算。反复分错的场景由第二层用户指令覆盖。

# 功能设计细节

本章是设计理念在关键问题上的具体裁决，直接规定实现方式。
## 储蓄目标

跟账本走。
## ai自动分类的原则
先检查用户有没有强制定义分类情况。没有则首先直接按朴素方式分类则直接分类。如果感觉不太好分类则按照用途来分。如果还是不太好分类则按照账本头的默认规则走。

举例：螺丝刀用户未定义，则按朴素分类？无法分类，按用途分类：螺丝刀可以用来修车，或者家用维修电器。可以划分为交通，居家。但按照默认规则，交通只能放直接开支，螺丝刀是因为能维修汽车才跟交通挂钩，居家（假设）没有太大限制，只需要满足居家使用/可以居家使用即可。因此划分为居家。

## 资产移动的处理

转账、垫付、借钱还钱不是消费也不是收入，单纯钱在挪窝。所以**不引入第三种类型，仍然记入收支，备注写明性质**：

- AA 垫付：垫付 200 → `支出 | 餐饮 | 200 | AA垫付`；同事转来 100 → `收入 | 其他收入 | 100 | AA收回`。净值 100，即真实花销。
- 借钱：借出 500 → `支出 | 其他 | 500 | 借给某人`；归还 → `收入 | 其他收入 | 500 | 某人还钱`。两笔归零，符合"并没有花掉"的事实。
- 用户内部转账，比如从支付宝转到微信，不记入账单。
## 升级动作

不提供「是否升级」的选择，也没有单独的「手动检查」按钮。更新的时机就是启动（刷新）时。检测到新版本即自动刷新加载最新资源，完成后仅弹出一次提示「升级好了 + 本次更新内容」。

更新提示只显示本次版本的更新内容（不管跨了几个版本）。设置页最后一条为「更新」，，无「发现新版本 / 正在自动升级」等文案。显示规则：当前版本 + 「启动时自动更新」开关 + 本版本更新内容。

开关关闭 = 纯本地运行（不检查也不更新）；手动打开开关时先检查一次，若有可升级版本，弹窗提醒「建议先备份账单，刷新页面将会更新」，点确认后返回界面（不自动刷新）。
## 信用卡与类信用工具（花呗、白条等）

核心规则：**一个经济行为只记一次，记在"获得商品/服务"的那一刻；资金清算不记。**

信用卡与普通借贷的本质区别：普通借贷中，借钱和花钱是两个独立事件，收支对冲后净值正确；而信用卡**刷卡瞬间借钱与消费同时发生、不可分割**，还款只是资金清算（存款→偿债）。若消费和还款都记支出，同一行为被记两次，月度支出系统性翻倍。

因此：

- **刷卡消费**：正常记支出（如 `支出 | 购物 | 240 | 买衣服`）。备注里带不带"信用卡"随用户，不影响统计。
- **还款**：不记账。用户提及还款时，AI 跳过并说明："信用卡还款不重复入账，刷卡消费时已记录。"
- **例外（真实费用要记）**：年费、分期手续费、利息是"购买银行服务"，记 `支出 | 其他`。
- 花呗、白条等类信用工具适用同一规则。

效果：信用卡在账本中完全隐形，账目反映消费事实而非资金管道。
## AI 整理（二期实现）

用户手动触发的账本整理功能：AI 通读当前账本，把错分的记录重新归入**当前账本分类表**内更合适的分类。备注措辞统一仅作可选项，默认不动备注（统一措辞是有损操作）。

操作时，逐条列出"哪条记录、从什么改成什么"（git 式前后对照），用户需要每一条选择同意或者不同意，再手动确认后才执行。采用”部分处理-执行-部分处理-……“的模式，允许未处理完成就退出，但要求增加二次确认，避免一不小心手滑直接退出，丢失所有修改。
## 分类变更与一致性校验

- **增加分类**：永远允许，不影响任何历史记录。
- **合并分类**：A 并入 B——所有引用 A 的记录改写为 B，账本头移除 A；执行前提示将改写的记录数，用户确认后执行。改名不需单独做：新增目标分类 + 合并旧分类即可。
- **删除分类**：仅当该分类下没有任何记录时允许。有记录则拒绝，提示用户先自行处理这些条目，处理后（改归其他分类或删除条目）才能删。
- **加载 / 导入校验**：读入账本时检查一致性——账本头声明了但没有数据引用的分类：无视，无所谓；记录引用了头部未声明的分类：正常流程不可能产生，只会是用户手改 md 造成的，提示用户并列出问题行，修正后方可使用。
## 时区

记账对时间有严格要求，这里直接获取设备的当前时间。不提供时区调整的选项。
# 实现细节/约束要求

实现优先纯 CSS / SVG / Canvas 手写，不引图表库，除非过于困难。

零外部资源：无 CDN、无网络字体、无框架、无图标库（图标用内联 SVG）。

版本检查：每次启动时请求服务器 `version.json`（`no-store`）与本地记录的「已加载版本」对比，检测到新版本即自动升级；可选不检查更新。流量不作为硬约束。静态资源增量由 HTTP 缓存协商实现。重新加载服务器最新静态资源时不动本地数据与核心配置。




字体：系统字体栈。

统计图表用纯 CSS / SVG / Canvas 实现，除非太过困难。

必须适配 iOS 系统。

本地存储防清理（数据在浏览器 localStorage，存在被系统/清理工具抹掉的风险）：
- 启动时调用 `navigator.storage.persist()` 请求持久存储。
- iOS 检测：非 standalone 模式且本地已有账本数据时，引导用户"添加到主屏幕"

不得有需要构建的步骤。依赖尽可能少。

文件组织：允许实现时依照实际开发情况按模块拆分多个 JS 文件。每个文件职责单一，便于审查与迭代修改。版本更新与缓存策略见上文『版本检查』。

关于账本关联的对话记录，localStorage 中建议按账本键单独存储，切换账本时保存/恢复各自的对话现场。非硬性要求。

配置分为账本挂钩配置和核心配置。后者主要是请求url和鉴权码等系统配置。前者自然跟账本md挂钩，后者只存本地缓冲。
# AI 对接

- 协议：OpenAI 兼容的 Chat Completions 接口（默认适配 DeepSeek，用户可换任何兼容服务）。
- Base URL / API Key / 模型名由用户在设置页配置，存 localStorage，用户浏览器直连 API，服务器只负责加载内容。
- 每次请求注入**当前日期**（设备本地时间），解析"昨天""前天"等相对日期必须准确。
- 要求模型返回结构化 JSON（操作类型：新增/修改/删除/拒绝 + 记录数组或拒绝原因），前端校验后执行。
- system prompt 中写死：退款规则、资产移动规则、信用卡规则、调整前缀规则（对应章节均已给出完整定义）；**分类表与分类规则均不写死，每次请求从当前账本的账本头读入**。
