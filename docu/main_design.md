# AI 记账 · 设计文档

版本：v0.3
状态：初稿，细节待迭代

**实现协作约定**：实现者（AI）在实现过程中遇到不理解或有歧义的要求时，必须停下来提问，禁止自由发挥。

## 1. 设计理念

本章描述产品的设计目标与导向，是后续一切章节的上游。任何功能、字段、分类的存废争议，回到本章裁决。

### 1.1 用户画像

**不为"管钱"，只为"知道钱花哪了"的人。愿意花 5 秒说一句话，不愿意花 30 秒点表单。**

主要用户是开发者本人，次要用户是非技术用户。

### 1.2 产品设计核心：只管记账，不干理财的活

只做"记账"工具，不当"理财"工具。理财管的是资产（多账户、对账、预算、还款）；记账只回答两个问题：**"这个月花了多少"、"都花在哪了"**。凡属于理财的功能，一律不做。

### 1.3 字段存废三问

任何信息要不要成为结构化字段，问三个问题：

1. 它参与统计吗？（统计页会为它出一个数字吗？）
2. 它能从用户的一句话里稳定推断出来，无论用户如何问吗？
3. 用户会自然而然地主动说出来吗？

**三个都是"是"，就在存储位置新增结构化字段。否则一律进备注。** 结构化保持极简。

应用示例：

- 分类：三问全过 → 结构化
- 支付渠道（微信/支付宝/银行卡）：不参与统计 → 不设字段；用户说了就留在备注，不说不问
- 购买目的：无法稳定推断 → 进备注
- 商户：进备注（"午饭 35 麦当劳"，信息自然包含）

## 2. 设计细节

本章是设计理念在关键问题上的具体裁决，直接规定实现方式。

### 2.1 开销/收入分类原则：按对象，不按目的

分类只问"钱花在了什么东西上，这个东西本身属性是什么"，不问"为什么花"。

举例：购买打气筒。打气筒是工具，按对象属性应归入"购物"。但它可以用来给自行车打气（为了锻炼，按目的该归"健康"），也可以给汽车打气（按目的该归"出行"）——目的依赖用户的内心动机，文本中通常不存在，AI 无法稳定推断，且同一物品的目的随情境漂移。统计的第一美德是一致：同一件东西永远进同一个桶。故取对象，不取目的。目的信息由备注承载（"打气筒 35 骑车"），需要时可事后挖掘。

### 2.2 资产移动的处理

转账、垫付、借钱还钱不是消费也不是收入，单纯钱在挪窝。所以**不引入第三种类型，仍然记入收支，备注写明性质**：

- AA 垫付：垫付 200 → `支出 | 餐饮 | 200 | AA垫付`；同事转来 100 → `收入 | 其他收入 | 100 | AA收回`。净值 100，即真实花销。
- 借钱：借出 500 → `支出 | 其他 | 500 | 借给某人`；归还 → `收入 | 其他收入 | 500 | 某人还钱`。两笔归零，符合"并没有花掉"的事实。

代价：钱收回之前，支出数字短期虚高——可接受的近似。

### 2.3 统计要回答的问题

统计页只回答四个问题：

1. 本月花了多少
2. 本月收了多少
3. 结余多少
4. 钱花在哪了（分类占比）

治理指标："其他"类占比单独可见。时间基准：自然月。相对日期（"昨天""前天"）解析必须在实现上保证准确。

### 2.4 信用卡与类信用工具（花呗、白条等）

核心规则：**一个经济行为只记一次，记在"获得商品/服务"的那一刻；资金清算不记。**

信用卡与普通借贷（2.2）的本质区别：普通借贷中，借钱和花钱是两个独立事件，收支对冲后净值正确；而信用卡**刷卡瞬间借钱与消费同时发生、不可分割**，还款只是资金清算（存款→偿债）。若消费和还款都记支出，同一行为被记两次，月度支出系统性翻倍。

因此：

- **刷卡消费**：正常记支出（如 `支出 | 购物 | 240 | 买衣服`）。备注里带不带"信用卡"随用户，不影响统计。
- **还款**：不记账。用户提及还款时，AI 跳过并说明："信用卡还款不重复入账，刷卡消费时已记录。"
- **例外（真实费用要记）**：年费、分期手续费、利息是"购买银行服务"，记 `支出 | 其他`。
- 花呗、白条等类信用工具适用同一规则。

效果：信用卡在账本中完全隐形，账目反映消费事实而非资金管道。

## 3. 产品定位

一个**自用**的自然语言记账 Web 应用。

一句话记住设计目标：**记账只需要一句话讲清楚花了多少钱，干了什么事，其他的全部放心交给 AI**。

参考体验：用户输入"今天买衣服花了 240，送朋友"，AI 解析并自动归类入账：支出 240，分类购物，备注"送朋友"。

## 4. 设计原则

1. **零摩擦录入**：输入框是唯一入口，打开就能记。
2. **语义专制，语法宽容**：分类、数据格式钉死，用户感知不到；输入格式给建议不给强制，解析不了就追问，绝不报错卡死。
3. **数据可携带**：全部数据就是一份 Markdown 文档，可导出、可导入、可直接阅读手改。
4. **纯前端**：一个 `index.html` + `icon.png` 等图标资源，扔到任何静态服务器（或双击打开）都能跑。

## 5. 用户与运行环境

- 主要用户：开发者本人；次要用户：非技术用户（iPhone，Safari 添加到主屏幕使用）。
- 目标环境：iOS Safari（主屏 standalone 模式）、Android Chrome、桌面浏览器三端跨平台。
- 部署：家庭 ARM 服务器 + 内网穿透，nginx 静态托管，Basic Auth 由部署层负责（不属于本应用）。

## 6. 核心交互流程

### 6.1 记一笔（主流程）

```text
用户输入自然语言 → 调用 LLM 解析 → 写入数据 → 回显确认
```

AI 记完必须立即回显结构化结果，例如：

> 已记 2 笔：餐饮 35.00（午饭）｜ 餐饮 18.00（咖啡）

回显即纠错入口：用户扫一眼就知道对不对。

### 6.2 调整

允许用户对话式纠错。为了降低解析出错的风险，用户在**记账时允许自由表达，而调整时必须以"更正""删除"开头**。没有指定记录则默认上一条，否则按指定日期或内容定位。这也能变相约束用户表达。

举例：

- 用户："更正：是 260" → 修改上一条记录金额。
- 用户："删除：10月1日午饭" → 删除指定记录。
- AI 回显："更正：已记 2 笔：餐饮 45.00（午饭）｜ 餐饮 18.00（咖啡）"

兜底：**手动编辑**——记录页与首页的条目可编辑（金额、分类、日期、备注等）、可删除。

### 6.3 模糊处理

AI 拿不准时拒绝记录，**必须附带而且只附带拒绝原因，且原因需具备引导性**，让用户能立即纠正。例如："未记录：无法判断分类，请补充说明（如'打车 20 交通'）"。

### 6.4 容错

- 发送失败（断网、API 故障）：输入内容保留到缓冲，每次重新打开都要询问用户是否需要处理。原文保留，带上时间前缀。用户说的话绝不丢失。
- API 未配置：引导用户去设置页，不阻塞浏览已有数据。

## 7. 数据模型

### 7.1 存储

唯一事实来源是一份 **Markdown 文档文本**，整体存放于浏览器 localStorage。App 内所有展示、统计均由解析该文档得到。导出 = 下载该 md；导入 = 替换该 md。

### 7.2 记录格式

一行一条，竖线分隔，追加式，行首无修饰符：

```text
2026-10-01 | 支出 | 餐饮 | 35.00 | 午饭
2026-10-01 | 收入 | 工资 | 8500.00 | 十月工资
```

字段：`日期 | 类型 | 分类 | 金额 | 备注`

- 日期：YYYY-MM-DD
- 类型：`支出` / `收入`
- 金额：两位小数；退款为负值（见 7.3），其余非负
- 备注：任意文本，不含竖线；渠道、目的、商户、资产移动性质等信息均在此承载（见 1.3、2.1、2.2）

### 7.3 退款

退款**不记收入**，记为对应支出分类的**负金额支出**：

```text
2026-10-01 | 支出 | 购物 | -59.00 | 衣服退款
```

使分类统计反映净花销。这是数据格式的硬约定。

### 7.4 资产移动

转账、垫付、借贷按 2.2 节规则记为普通收支，备注写明性质（"垫付""收回""借给某人""某人还钱"），不引入新类型。

### 7.5 对话记录

用户输入与 AI 回显构成对话流（微信式），**对话记录持久保存**（localStorage 独立键，不属于账本 md），重新打开后历史对话可见、可回溯。

## 8. 分类体系

封闭分类表，AI 只能从中选择，禁止自创。用户暂不可增删（"其他"兜底）。分类按对象不按目的，见 2.1。

**支出分类（10 个）**：

餐饮、交通、购物、居家、娱乐、医疗、教育、通讯、人情、其他

**收入分类（3 个）**：

工资、理财、其他收入

**待定事项**：是否开放用户自定义分类（物品属性存在交叉，分类天然主观）。v1 冻结为封闭表，后续版本再议。

## 9. 页面结构

单页应用，底部 Tab 切换四个视图，移动端优先。

### 9.1 概览（首页）

- 本月支出 / 收入 / 结余三个数字。
- 个性化区：本月存钱目标及当前进度（简单配置，存 localStorage）。
- 设置入口放本页右上角。

### 9.2 记账（微信对话框式）

- 主体为**对话流**：用户输入与 AI 回显以聊天气泡形式呈现，对话记录持久保存（见 7.5）。
- 当天记入账目内嵌于对话流中，可直接点击修改。
- 底部：输入框 + 发送按钮。输入框聚焦时正常弹起，不被键盘遮挡。

### 9.3 统计

回答 2.3 的四个问题，图表俱全：

- 柱状图：各支出分类金额对比
- 饼图：支出分类占比
- 折线图：收支随时间趋势（近若干月）
- "其他"类占比单独可见

实现优先纯 CSS / SVG / Canvas 手写，不引图表库，除非过于困难。

### 9.4 明细

全部账单按条目展示，按时间线排列，支持**搜索**（按备注/分类/金额），支持**按时间切换**（按月浏览）。条目可编辑、可删除。

### 9.5 设置

抽屉或独立视图：API Base URL、API Key、模型名；md 导出 / 导入；分类表只读展示；存钱目标配置。

### 9.5 iOS 适配要求

standalone meta、apple-touch-icon（icon.png）、安全区适配（env(safe-area-inset-*)）、输入框不被键盘遮挡。

## 10. AI 对接

- 协议：OpenAI 兼容的 Chat Completions 接口（默认适配 DeepSeek，用户可换任何兼容服务）。
- Base URL / API Key / 模型名由用户在设置页配置，存 localStorage，浏览器直连 API。
- 每次请求注入**当前日期**（解析"昨天""前天"等相对日期，见 2.3）。
- 纠错请求携带最近 10 条记录作为上下文（支持 6.2 的对话式纠错）。
- 要求模型返回结构化 JSON（操作类型：新增/修改/删除/拒绝 + 记录数组或拒绝原因），前端校验后执行。
- system prompt 中钉死分类表（第 8 章）、退款规则（7.3）、资产移动规则（7.4）、信用卡规则（2.4）与调整前缀规则（6.2）。

## 11. 非功能约束

- 单文件 HTML（CSS/JS 全部内联，除非确实条件不允许/工程管理太困难），总体积软性目标 < 50KB。
- 零外部资源：无 CDN、无网络字体、无框架、无图标库（图标用内联 SVG）。
- 字体：系统字体栈（-apple-system, "PingFang SC", "Microsoft YaHei", sans-serif）。
- 无构建步骤，原生 ES2017+。
- 统计图表用纯 CSS / SVG / Canvas 实现，除非太过困难。

## 12. 部署架构（简述）

Rock64（Armbian）+ nginx（gzip、长缓存头、Basic Auth）+ 花生壳内网穿透。详见实现文档。
